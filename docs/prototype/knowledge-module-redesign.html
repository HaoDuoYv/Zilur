Product Prototype · v4 · 2026-10-02

知录 · 知识点记录模块重新设计

强调体系为三层：L1 块级（整条小点的左缘色条 + 8% 淡底 + 角色标签）、 L2 行内（选区 → 起色，单个字也能变色）、L3 弱强调（加粗 **文字**，无色）。 v4 解决"语法用户写不来"这个根本可用性问题：内联语法是存储格式，不是交互 —— 用户在任何状态都看不到 {{ }}，也永远不需要打它。 机制不是"渲染时藏起来"，而是标记根本不进编辑缓冲：激活块时拆成 可见文本 + span 表，编辑全程发生在可见文本上，保存时才物化回 content。这样光标、选区、输入法全是原生文本行为， 退格不可能删到标记（详见画板下方的规范区）。
屏 1 静态效果、屏 2 划词起色、屏 3 折叠扫描、屏 4 块级标记、 屏 5 语法对照（只读 / 编辑 / 标记中，可切换）。

内联语法 {{ }}

语法活在 Block.content 文本里，所以导出 / 导入 / 剪贴板 / AI 全部天然承载， 不存会随编辑漂移的字符 offset。角色前缀必填：没有裸写形式，也不存在"最近一次使用的角色"这类会话状态， 同一段文本在任何时候渲染结果都一样。

语法定义

统一用 {{ }} 包裹，一套符号管到底

{{k:文字}} 要点 KEY · 荧光笔（默认）
{{i:文字}} 想法 IDEA
{{w:文字}} 注意 WARN
{{t:文字}} 待办 TODO
{{k-c:文字}} 纯变色（只改字色，无底）
{{k-u:文字}} 下划线（变色 + 底线）
\{{   \}} 转义，输出字面量本身
**文字** 加粗 —— 既有语法，不新增

解析优先级

与既有行内格式合并成一个词法器，左起最先匹配者胜

1 `代码` 内部一律不再解析
2 $公式$ 行内 LaTeX → 图片（既有）
3 **粗体** 既有能力，不变
4 {{角色:内容}} 本次新增

{{...}} 的内容内不再解析其它标记（含 $公式$）： 公式请写在标记之外，例如 {{k:唯一确定}}$x^2$。

为什么不是 [[ ]]

原稿断言"只有代码会冲突"，被本原型自己推翻了

数学里的嵌套数组：[[1, 2], [2, 1]]
Obsidian / Markdown 的 wiki-link：[[笔记名]]
C++ 属性：[[nodiscard]]
按旧规则（[[ 后可"直接是内容"），第一行会被解析成"把 1, 2], [2, 1 着色"——静默改变正文外观。

不会被误解析的正文（逐字原样显示）

容错是硬要求：AI 与用户都可能写错，写错不能造成正文缺失或变形

正文写法 结果 原因
[[1, 2], [2, 1]] 原样显示 不以 {{ 开头，不构成标记
A = Aᵀ 原样显示 等号不再是标记字符
if (a == b) 原样显示 同上（原稿担心过的 == 冲突已不存在）
{{1, 2}} 原样显示 角色字母不合法（必须为 k / i / w / t）
{{k:}} 原样显示 内容为空
{{k:未闭合 原样显示 未成对
{{k:含 }} 的内容}} 原样显示 内容不得包含 }}（不支持嵌套）
{{k:文字}} 着色文字 唯一成立的形式

编辑期边界规则（adjustSpans）

标记不进编辑缓冲后，真正要定义清楚的是"这次编辑让已有的 span 怎么变"。 这张表是穷举单测的规格，不是"看起来合理就行"——边界语义不定死，"在标记末尾继续打字"就会时对时错。

编辑动作 span 处理 理由
在 span 内部插入 扩展 明显
在 span 末尾插入（caret == end） 扩展 "我在接着写这个要点" —— 高频意图
在 span 起始插入（caret == start） 不扩展 "新写的字不属于这个标记"
删除与 span 相交 按交叠长度收缩
删除完全覆盖 span 删除该 span 文字按用户选择删，意图明确
零长 span（「标记中」）处的输入 扩展 「标记中」就靠这一条实现
粘贴 / 输入含换行 在换行处断开 内联标记不跨行
全选删除 span 全清

为什么不用 VisualTransformation

"让标记不可见"有两条路，这是被否掉的那条以及替代它的那条

方案 问题 / 结果
VisualTransformation
+ 自定义 OffsetMapping		 它只改渲染与命中测试，不改编辑语义。缓冲里仍是带标记的全文，退格按原坐标删字符 —— 光标停在内容开头按退格，删掉的是 : 而不是前面的字。 要修就得再叠一套"编辑意图修复"；而它与中文输入法组合输入（composing）的组合 是 Compose 文本里最容易出 bug 的地方，风险全落在只有真机能验的地方。
可见文本缓冲
+ 会话内 span 表 采用		 编辑缓冲里根本没有标记，光标 / 选区 / 输入法全是原生文本行为。 落库仍是 content 文本（标记跟着字符走）， span 表是会话内派生物、随时可从文本重建 —— 因此只有一个真相，不是"offset 又回来了"。 全部风险集中在三个纯函数（parseSpans / materialize / adjustSpans）上，可穷举单测。

色源与分工（v3 修正）

一色一义：身份色与内容色必须同族、不同值、不同位置

用途 来源 取值 出现位置
语义角色（内容） AccentPalette.primary 赭土 #7C5C31 / 苔绿 #4B6B4F / 绛红 #8A4550 / 松石 #3D6E6B 行内底色 20%、块级左缘 3dp 条、角色标签词
卡片身份（容器） TagColors 7 色低饱和批次（#4A5C7A 墨蓝起） 序号徽标底色 12%、心线 26%、折叠竖条
主题强调色（控件） AccentColor 7 色，用户在设置里可换 聚焦描边、按钮、图标

卡片身份色刻意不用 AccentPalette 的 primary：赭土 / 苔绿 / 绛红 / 松石 这 4 个 primary 与 4 个语义角色逐值相同，会让"卡片 02 的心线"和"这条小点的要点标记"变成同一个颜色。 TagColors 是同一色相家族的低饱和版本，既不与语义色撞值，也与标签胶囊一致， 而且"身份色比内容色更淡"正好符合「容器让位于内容」。

三层强调的分工：L1 块级 = 一整条小点的性质（要点 / 想法 / 注意 / 待办）； L2 行内 = 句中的关键字，字级生效，单个字也能变色，三种笔触都写在语法里； L3 弱强调 = 加粗（**文字**），无色。 行内着色复用块级那套 4 角色色，但取「加深墨色」（--key-ink 等）以保证小字可读。
v3 的两条修正：语义色派生自既有 AccentPalette（不新写色值）； 卡片身份色改用 TagColors 低饱和批次（AccentPalette.primary 与 4 个语义角色逐值撞色）。
v4 的关键：内联语法是存储格式，不是交互 —— 用户在任何状态都看不到、也不需要打 {{ }}。所有着色动作都是"选字 → 点色块"或"点色块 → 接着打字"， 全程零输入；标记只在保存那一刻物化进 content。

取自 TagColors 低饱和批次；仅作用于徽标底色 / 心线 / 折叠竖条，不整卡染色

使用约束

防止"处处高亮 = 没有高亮"

行内着色占比建议 ≤ 20%
单块最多角色数2 种
WARN 与报错红不同时出现
语义色随主题变不跟随
身份色与内容色同族不同值
