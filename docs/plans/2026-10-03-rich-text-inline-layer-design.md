# 富文本行内层设计（InlineNode over 单一文本缓冲）

状态：设计中（P0 待验证）
适用版本：Compose foundation 1.7.4 / material3 1.3.0（`app/build.gradle.kts`）

---

## 1. 目标

让 TEXT 块里的四类内容都成为**原子对象**：

1. **公式**：写对了在编辑态就渲染成公式图；可整体选中、可着色、可整体删除，永远不可能被标记住"切一半"；
2. **行内代码**、**行内链接**：同上（可见、可整体选中、可整体着色）；
3. **语义标记**（要点/想法/注意/待办 + 三种笔触 + 加粗）：与上述原子共存，行为不变。

一句话验收：**在编辑态写 `$W \le 2^{n-1}$`，它当场变成公式图；选中它点「要点」，它变成要点色；整个过程公式源码一字未改。**

## 2. 非目标

- **不合并块类型**（见 §4）；
- **不改落库格式**（见 §5）；
- 不做协同编辑、不做完整 Markdown 所见即所得（只覆盖已存在的这四类）；
- 不重写 AI 工具契约、导出、搜索、摘要。

## 3. 现状与痛点（都有真机证据）

| 现状 | 后果 |
| --- | --- |
| 编辑器是 `BasicTextField`，`buildToneStyledText` **刻意不解析** `$…$` / 反引号（§3.7 约定） | 编辑态只能看 LaTeX 源码 |
| 公式图是 `InlineTextContent`，**只有 `Text`/`BasicText` 能画**；当前版本的 `BasicTextField` 没有 `inlineContent` 参数 | 这是"编辑态不渲染公式"的**技术根因**，不是漏做 |
| 选区可以落进 `$…$` 源码中间 | 标记被织进 `_{\text{发}}` 的花括号，写出 `{{w:$W_}}{{{w:\text}}…` 这种读不回来的碎片 |

第二、三条已经在上一轮打了补丁（选区向外吸附 + 语法允许整条公式被包住 + `canCover` 拦半截），
**本设计是把补丁升级成正解**：不是"拦着用户别切坏"，而是"公式根本不是可以切的东西"。

## 4. 核心决策一：块层保持分离，行内层加厚

**问题**：普通文本 / 公式 / 代码 / 链接，做了富文本之后是合并进一个富文本块，还是保持分开？

**结论：按"是否参与句子"分两层，不是二选一。**

| 元素 | 行内形态（句子的一部分） | 块形态（独立单元） | 决策 |
| --- | --- | --- | --- |
| 普通文本 | — | `TEXT` 块（**就是富文本的载体**） | 保留为块 |
| 公式 | 行内 `$…$` | `LATEX` 块（居中、可编号、可单独排序） | **两种都要** |
| 代码 | 行内 `` `x` `` | `CODE` 块（多行、语言、复制、换行策略） | **两种都要** |
| 链接 | 行内 `[文字](url)` | `LINK` 块（书签卡片：标题 + 摘要 + 缩略图） | **两种都要** |
| 待办 / 分割线 / 分支 / 图片 | — | 现有块类型 | 保留为块 |

**为什么块层不能合并进富文本**（这是本设计最要紧的一条）：

1. **块层承载结构**：拖拽排序、卡片分组、`BRANCH` 的父子嵌套、小节折叠 —— 全是以"块"为单位。
   合并成一篇大富文本，等于把"知识点 = 小节 + 块"这个产品骨架拆掉；
2. **块层是 AI 的粒度**：10 个工具（`add_blocks` / `update_note` / `set_block_emphasis` …）
   的 schema 就是块，合并后整套契约要重写，风险极大而收益为负；
3. **块的读法不同**：代码块要横向滚动、语言高亮；公式块要居中；书签卡片要抓取元信息 ——
   这些都不是"一段文字"，塞进同一个文本缓冲只会互相将就。

**代价与对策**：两层并存会出现"我想把这段公式单独拉出来"的需求，
所以必须配套 **行内 ↔ 块** 的转换（§9 P3）：行内公式 → 提升为 `LATEX` 块；反之亦然。

## 5. 核心决策二：落库格式一个字都不改

现有存储形态（`Block.content`）：`{{k:要点}}`、`$…$` / `$$…$$`、`` `code` ``、`**粗**`、转义 `\{{` `\}}`。

**富文本是"编辑与渲染层的重构"，不是"存储层的重构"。**

`InlineNode` 是**从同一份存储派生出来的视图模型**（和今天的 `visibleText + List<InlineSpan>` 是同一性质），
不是新的落库结构。因此以下全部**零改动**：

- AI 工具写入路径（`AiToolExecutor` → `normalize`）、系统提示词、schema；
- 导出（JSON / Markdown / HTML / `.dtk`）、备份恢复（`BackupRestore`）；
- 搜索（`NoteFind`）、列表与卡片摘要（`InlineMarkup.toPlainText`）、AI 摘要；
- 剪贴板块序列化、数据库（**不需要 Migration**）。

这条决策把整个工程的风险砍掉一大半：**没有数据迁移，回滚就是回滚代码。**

## 6. 核心决策三：坐标系统一在"可见文本"上

今天 `InlineSpan` 的坐标是"块内**可见文本**偏移"（标记字符已剥离）。
富文本继续沿用这套坐标，只把"可见文本"的含义明确为：

> 可见文本 = 剥离 `{{}}` 语法字符之后的正文，**其中 `$…$`、`` `…` ``、`[文字](url)` 的源码仍占位**。

于是：

```kotlin
/** 行内原子：可见文本上的一个区间 + 它的种类。 */
data class InlineNode(val kind: InlineKind, val start: Int, val end: Int)
enum class InlineKind { MATH, CODE, LINK }
```

- `InlineSpanAdjuster` 的 8 条规则**原样复用**：原子和标记一样，只关心 `start`/`end`，
  文字增删时自动伸缩/断开/丢弃 —— 一行都不用改；
- `InlineMarkup.materialize` 的输入输出不变（它已经在处理 `$…$` 与转义）；
- 原子的边界计算复用上一轮新增的 `MathSpans`（它已经是"可见文本 → 区间"的形状，
  扩展成 `InlineNodes.ranges()` 即可，`MathSpans` 作为它的 MATH 实现保留）。

## 7. 编辑器实现：单缓冲 + 源码透明 + 覆盖层

> 本节已被 P0 修订（见 §8）：原计划的"折叠成 0 宽"**实测不可行**，改为"源码透明 + 保留宽度"。

**不用**"每段一个 `BasicTextField`"的多字段方案（C1）：焦点、跨段光标、退格合并、选区跨段、
IME、撤销全部要自己写，且会破坏"一个块一个缓冲区"的现有不变量。

采用 **单缓冲 + `VisualTransformation` 隐藏源码 + 覆盖层绘制**：

```
Block.content（存储形态）
      │ parseSpans / InlineNodes
      ▼
可见文本 + List<InlineSpan> + List<InlineNode>        ← 会话内状态
      │
      ├── VisualTransformation：把**非活动**原子的源码设成 Transparent
      │      （只改样式、不改长度 → 偏移映射是恒等的）
      │
      ├── onTextLayout：用 getCursorRect 拿到原子自己占的那个盒子
      │      → 覆盖层在这个盒子里画公式图 / 代码片 / 链接
      │
      └── 光标进入某原子 → 该原子**恢复可见**（Notion 式）
             恢复期间它就是普通文字，可正常编辑 LaTeX
```

这套方案实测的三条好处（§8.2）：**无需 `OffsetMapping`、覆盖层不遮挡后文、跨折行定位正确**。

## 8. P0 技术验证（结论：已跑，方案已调整）

试验屏：`app/src/debug/java/com/example/zhilu/debug/P0SpikeActivity.kt`（**只在 debug 变体，不进正式包**）。
拉起：`adb shell am start -n com.example.zhilu/com.example.zhilu.debug.P0SpikeActivity`。
屏上直接打印几何诊断，下面的数字都是真机实测（1440×2560，字体 17sp）。

### 8.1 被否掉的方案：把原子折叠成 0 宽

| 验证项 | 结果 |
| --- | --- |
| 折叠 + `OffsetMapping` 双向映射 | **可用**（84 → 40 字符；`originalToTransformed` 正确，反向映射需注意取"折叠区间起点"而不是 `index-1`） |
| `onTextLayout` 定位原子 | **可用**：`getCursorRect` 给出精确 `x/y/height/line`，**跨折行也对**（atom2/3 正确落在第二行） |
| 覆盖层是否会压住后文 | **会，致命** ❌ 折叠后原子不占宽度，覆盖层画上去直接盖住后面的文字（截图可见"原子0"紫块压住「与 说明」） |

结论：**折叠成 0 宽这条路不走**。它要求覆盖层"凭空占位"，而文本布局不会为它留空间。

### 8.2 采用的方案：源码透明 + 保留它占的宽度

`VisualTransformation` 只改样式（原子区间 `SpanStyle(color = Transparent)`），**不动文本长度**。

| 验证项 | 实测结果 |
| --- | --- |
| 偏移映射 | **恒等映射**（布局长 = 原长 = 84）→ 不需要 `OffsetMapping`，第一类 bug 整体消失 |
| 覆盖层落位 | **正好落在源码占的空位里**，后文一个字未被遮挡 ✅ |
| 跨折行 | 正确（atom2 `x=425 y=160`、atom3 `x=833 y=160`，与第二行文字同基线） |
| 原子源码占宽（实测） | atom0 `$W_{\text{发}} \le 2^{n-1}$` = **791px**；atom1 `$a+b$` = 190px；atom2 `` `code()` `` = 238px；atom3 `$x^2$` = 176px |

### 8.3 唯一遗留问题（已量化，P1 解决）

**源码占宽 ≠ 渲染图宽度**：atom0 源码占 791px，公式图实际约 300px，中间会留一块空白。
三个候选，P1 先用第 1 个跑通，再按观感决定是否升级：

1. **图片缩放到盒子宽度**（含上限，避免过度放大）—— 最简单，无映射改动；
2. **压缩源码字距**：源码是不可见的，负 `letterSpacing` 压到目标宽度不会难看，但会影响选区矩形；
3. **占位符方案**：把原子替换成 k 个不换行空格（宽度≈k×空格宽）+ 字距微调，`OffsetMapping` 处理长度差 —— 最精确，但把映射复杂度又请回来了。

### 8.4 仍需手动确认（P1 真机操作）

- **IME 组词**：光标进原子后打字是否正常（当前方案里原子是可编辑实体，需要"活动原子展开显示源码"的交互）；
- **TalkBack**：原子需要自带 `contentDescription`（公式读源码、代码读内容），否则读屏只能读到空白；
- **选区观感**：选中原子时高亮会盖在透明源码上 —— 预期正好是"选中了整个公式"的观感，待确认。

### 8.5 P0 结论

设计文档 §7 的"折叠渲染"改为 **"透明保留宽度"**；`InlineNode` 与坐标系统（§6）**不受影响**（反而更简单：恒等映射）。
P1 可以直接开工，遗留的两项按 §8.3、§8.4 处理。

## 13. P2 实施记录（行内代码）

### 13.1 行内代码与公式**不是同一种原子**

| | 公式 | 行内代码 |
| --- | --- | --- |
| 渲染 | 图片（异步渲染，尺寸事先未知） | 就地套样式（等宽 + 淡底色），与只读路径同一套观感 |
| 源码 | **隐藏**（透明），由覆盖层补画 | **照常显示** |
| 覆盖层 | 需要 | 不需要 |
| 控盒 | 需要（源码占宽 ≠ 图宽） | 不需要 |

原因是两者的"盒子"性质不同：公式要画一张尺寸未知的图，所以必须先把源码的位置和宽高腾出来；
行内代码本身就是文字，套个样式即可 —— 多走一套覆盖层只会平白引入几何问题。

### 13.2 行内代码有"原子性"吗

**没有做选区吸附之外的额外限制**，这是有意的：公式必须吸附/包整条，是因为 `{{k:…}}` 塞进
LaTeX 的花括号之间会写出读不回来的碎片（真机踩过）；行内代码里没有花括号，
标记切进代码内部写出来仍然是**合法且可读回**的形态：

```
调用 `code()` 即可   →  选中 "co" 加色  →  调用 `{{k:co}}de()` 即可   →  读回可见文本一致
```

所以 P2 只把**选区吸附**（`InlineNodes.snapOutside`）推广到所有原子，让"选一半代码"也变成"整条"，
但不做"禁止标记"那一道 —— 那是公式专属的、由存储形态决定的约束。有单测锁住这条往返。

### 13.3 行内链接：已实现（用户确认"自动识别"）

现状与决策：正文原先**没有**行内链接语法（`[标题](url)` 只出现在 Markdown 导出里）。用户拍板
**自动识别**，落地前专门查过全库含 `](` 的块数 = **0** → 不改写任何既有内容。

实现（与行内代码同形：**就地套样式**，不隐藏源码、不用覆盖层）：

| 层 | 内容 |
| --- | --- |
| domain | `InlineKind.LINK` + `InlineNodes.inlineLink` 正则（单行、非空）；选区吸附自动覆盖它 |
| 编辑态 | 强调色 + 下划线，显示 `[文字](url)` 全文（要能改） |
| 只读态 | 只显示**文字**（不显示 URL）+ 强调色 + 下划线 |
| 落库 | 仍是纯文本 `[文字](url)`，**格式未变** |

坑：`buildInlineLatexText` 是**普通函数**（非 @Composable），读不了 `MaterialTheme` ——
链接色改为 `linkColor` 参数传入。**`RichText` 是它唯一的调用点**（已查证），无需再接别处；
AI 消息气泡用自己的渲染路径（`AiMessageContent`），与本函数无关。

**验证状态**：编辑态与只读态**都已真机确认** —— 编辑态显示 `[文档](https://a.b)` 全文（强调色 + 下划线），
只读态只显示「文档」；两处库里存的都仍是原文，格式未变。

## 12. P1 实施记录

### 12.1 落地的东西

| 文件 | 作用 |
| --- | --- |
| `domain/markup/InlineNodes.kt` | 行内原子模型（`InlineNode` + `InlineNodes.of/hidden`）。坐标与 `InlineSpan` 一致，纯函数、有单测（7 条） |
| `ui/note/blocks/InlineAtomLayer.kt` | `HideAtomsTransformation`（源码透明、长度不变）+ `InlineAtomLayer`（在源码让出的空位里画公式图） |
| `ui/note/blocks/TextBlockEditor.kt` | 接入：`visualTransformation` + `onTextLayout` + `decorationBox` 里的覆盖层 |

关键实现点：

- 覆盖层放在 `decorationBox` 的 `Box` 里，与 `innerTextField()` **同坐标系** → 不需要手工补 padding（P0 试验屏里是手工补的，正式实现不需要）；
- 原子区间**每次从 buffer 现算**，不落状态 → 文字增删时自动伸缩，`InlineSpanAdjuster` 一行未改；
- 活动原子（光标所在）**不隐藏**，恢复成可编辑源码 → 这同时解决了"公式怎么改错字"和"折叠态光标没有落脚点"两个问题；
- 渲染失败或尚在渲染时，覆盖层退回显示源码小字 → 公式写错时用户仍能看见并修。

### 12.2 真机验证结果（1440×2560）

编辑态打开含公式的笔记：`n = 编号比特数`、`序号空间 = 2^n`、`W_收 = 1 →`、`W_发 ≤ 2^n − 1`、`2W ≤ 2^n`
**全部渲染为公式**；被标记覆盖的那条 `W ≤ 2^{n-1}` **带着标记底色**。
→ **"编辑态渲染公式"与"公式跟随标记着色"在编辑态均达成。**

### 12.3 观感问题与处理进度

**根因**：覆盖层的盒子 = "源码占宽"，而源码（如 `$W_{\text{收}}=1$`，实测 791px）通常比渲染图宽得多。

已做（第 3 轮）：

- **左对齐替代居中** ✅ 居中会让公式看上去被推向中间、和缩进对不上；左对齐读成"公式后面跟了个空格"，
  真机截图确认明显改善（`GBN：代入 W_收 = 1 →`、`→ 2W ≤ 2^n`、带标记的 `W ≤ 2^{n-1}` 都正常了）；
- **去掉人为的缩放上下限**（原来 `coerceIn(0.5, 1.6)`）：改为"宽或高至少一边贴齐盒子"，
  公式不再忽大忽小。

仍遗留：

1. ~~宽原子后会留一段空白~~ → **已解决**（第 4 轮）：给不可见的源码设负 `letterSpacing`，
   把它的占宽压到与图一致。真机上 `GBN：代入 W_收 = 1 → W_发 ≤ 2^n − 1` 现在紧凑排在一行。
2. ~~含 CJK 的公式偏小~~ → **大幅改善**：给源码设更大的 `fontSize`（上限 2.2×）把行高撑到图高。
   仍有边角：**被折行截断的原子不参与控盒**（宽度跨行没有意义），这类公式仍按行高封顶缩小。

### 12.4 控盒的坑：反馈环必须设上限（第 4 轮踩到）

控盒本质是"测量 → 改样式 → 再布局"的**反馈环**，模型（字号↔宽高的线性假设）不可能完全准。
第一版没有上限，真机上编辑页空闲 CPU 直接 **32~38%**（在反复布局，`top` 里稳居前列）。
加了三道保险后回落到 `top` 都刷不出来的水平：

1. 每个原子**最多调 3 次**（`MAX_TUNING_PASSES`）—— 从构造上保证收敛，这是关键的一道；
2. 每轮只走 **60%** 的修正量（`TUNING_DAMPING`），避免在目标附近过冲；
3. 阈值放宽到 4px / 0.05 倍字号，差得不够多就不动。

**教训**：任何"布局 → 测量 → 改状态 → 再布局"的回路，都必须先想好它在什么条件下**停下来**。
只靠阈值不够 —— 阈值附近来回震荡同样能耗满 CPU。

### 14.5 未结：编辑态「含 CJK 的公式偏小」—— 已定位到机制冲突

**现象**：编辑态里 `$W_{\text{发}}=W_{\text{收}}=W$` 这类含 `\text{}` CJK 的公式，比只读态（以及不含 CJK 的公式）看起来小。

**真机实测数据**（临时 `Timber.d` 探针，定位后已撤）：

```
atomDraw start=79 img=209x75 box=208.0x104.0
atomTune wrapped start=79 img=209x75 boxH=104.0 scale=1.00→1.00 pass=2
```

**排除掉的三个猜测**：控盒**已收敛**（盒宽 208 ≈ 图宽 209）；`atomSizes` **已收到**；覆盖层**走到了**预期分支。

**定位到的真正原因 —— 两个机制在互相抵消**：

1. 控盒把**不可见源码的占宽压到与图宽一致** → 于是覆盖层里 `boxWidth / image.width ≈ 1`；
2. 而缩放式是 `scale = min(boxWidth/image.width, heightLimit)` → **宽度那一项把缩放锁死在 1**，
   所以"把图放大到填满行高"这一步永远轮不到（本例需要 1.3× 才能填满 104px 的行高）。

也就是说：**控盒为了让排版紧凑把宽度对齐了图，而"让公式填满行高"需要图比盒子宽出放大倍数**。
两者目标冲突，当前实现选了前者，于是含 CJK（图高被 `\text{}` 的行高抬高、主符号相对更小）的公式显得小。

**候选修法**（下一轮选一条验证，别直接改）：

1. **把控盒的目标从"图宽"改成"图宽 × 目标缩放"**：先定 `目标高 = 0.9 × 行高`，
   得出 `缩放 = 目标高 / 图高`，再让盒子宽度 = `图宽 × 缩放`；覆盖层按同一缩放绘制。
   这样两者不再冲突，且与只读态（占位高 = 图高、行高随图长）的观感一致。
2. 只对"图高 < 行高"的原子走放大，简单但要小心与只读态的观感反过来。
3. 接受现状：超长/含 CJK 的公式本就该用「转为公式块」（该出口已做好并有真机验证）。
