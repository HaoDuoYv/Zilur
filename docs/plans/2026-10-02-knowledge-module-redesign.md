## 0. 结论摘要（TL;DR）

四条问题有**一个共同根因**：卡片内每个小点都是同款「白底 + 1dp 描边 + 16dp 内边距」的圆角卡片，
信息层级被"容器"吃掉了。

| 问题 | 对策（一句话） |
| --- | --- |
| 无关键内容颜色强调 | 两层强调：**L1 块级**（整条小点的 4 角色语义色）+ **L2 行内**（任意单字/词组的字符级着色） |
| 小点结构不清晰 | 撤掉块级描边，改为**结构化行**：左侧固定 gutter 放序号，用**连续心线**串起同卡小点，跨类型用间距节奏分层 |
| 知识点间区分度不足 | **卡片身份系统**：序号徽标 `01/02/03` + 卡片强调色（显式轮转序、可改）+ 标题/摘要 + 可折叠 |
| 小点多时定位困难 | **右缘索引轨**（拖动 scrub）+ **页内目录 sheet** + **sticky 卡头**，三层递进、按内容量自动出现 |

三项顺带发现：**术语自相矛盾**（§1.3，必须先修）、**已存在一套行内语法但无人声明**（§0.5 第 4 条，
本方案必须与它合并而不是并行新增）、**`Block.content` 的所有读取方都要处理语法**（§3.10，原稿漏项最多的一节）。

## 1. 现状诊断

### 1.1 当前结构

```
Note（笔记）
└─ KnowledgeCard × N            ← 用户口中的「知识点」，代码里叫「知识卡片 / 知识小点」
   └─ Block × M                 ← 用户口中的「小点」
      └─ Block × K（BRANCH 的子块，parentBranchId 指向父分支）
```

- 卡片外壳：`Surface(白底) + Modifier.border(1dp outlineVariant) + shapes.medium`，聚焦态换成 2dp 主色描边 + 阴影 0→8dp
  （`KnowledgeCardItem.kt:104-112`；`AppCardStyle.borderWidth = 1.dp`、`ElevationTokens.Card = 0.dp`）。
  `isFocused = card.isFocused && isEditing`，**只在编辑态渲染**（同文件 :78）。
- 卡片头：`📌 图钉 + 可编辑标题`，就这两样（`CardHeader.kt:43-78`；图钉 `contentDescription = "知识小点"`）。
- 小点外壳：**又一个** `Surface(白底) + BorderStroke(1dp, outlineVariant) + 16dp 内边距 + 12dp 内间距`，
  类型图标只在"激活且编辑"时才出现（`BlockCard.kt:102-114`；装饰行门控 `showDecorations = isEditing && isActive` :92）。
- 小点间距：基础 `BlockGap = 8.dp` 均匀间隔，再叠加额外 `padding(top)`：同类 8dp / 跨类 16dp / 遇分割线 24dp；
  同类相邻还会插一条 1dp 发丝线（`CardBlockList.kt:35, 121-132`）。
- 正文**编辑态**是纯文本 `BasicTextField`（`TextBlockEditor.kt:27-46`），**只读态**已走 `RichText` 解析
  `` ` `` / `**` / `$`（`BlockContent.kt:55-60` → `ExpandableBlockContent.kt:30-42` → `RichText.kt`）。
- 页面是单个 `LazyColumn`，**没有任何页内导航设施**（`NoteEditScreen.kt:245-383`）；
  卡片 = 一个 lazy item（`key = card.id`），**卡内的块不是 lazy item**（`CardBlockList` 是普通 `Column`）。

### 1.2 根因归因

1. **套娃卡片**：白卡里套白卡，两层描边只差 1dp 粗细、颜色同为 `outlineVariant`。视觉上既是"一叠一样的白片"，
   又让"间距节奏"完全读不出来——因为间距被描边框住了，人看到的是"框与框的间隙"而不是"内容的呼吸"。
   → 直接造成问题 2（结构不清晰）与问题 3（区分度不足）。
2. **唯一的身份表达是图钉**：卡片之间只有标题文字不同，且标题字号 `cardTitle 17sp` 与小点正文 `body 16sp` 接近，
   扫视时无法快速切分章节。 → 问题 3。
3. **颜色只用于"标签"与"焦点"**：`TagColors` 给标签胶囊，`colorScheme.primary` 给聚焦描边/图标/按钮，
   正文里没有任何**语义色相**能力（已有的三种行内格式都是无色的）。 → 问题 1。
4. **扁平的一次元列表**：卡片与小点混在一个 `LazyColumn` 里顺序滚动，没有目录、没有索引、没有折叠，
   而且卡内块不参与懒加载。 → 问题 4，并带来大卡首帧成本（§6.6）。

### 1.3 顺带发现：术语混乱（建议先修）

| 位置 | 当前用词 | 实际指代 |
| --- | --- | --- |
| `AddKnowledgeCardButton`「添加新的知识小点」 | 知识小点 | **卡片**（KnowledgeCard） |
| `CardHeader` placeholder「输入小点名称(如:情况一)」 | 小点 | **卡片** |
| `CardHeader` / 图钉 `contentDescription「知识小点」` | 知识小点 | **卡片** |
| `TagsScreen`「「{标签}」下的知识点」 | 知识点 | **笔记**（Note） |
| AI 系统提示「创建、整理、修改知识点」 | 知识点 | **笔记** |

同一个词「知识点」既指笔记又指卡片；「小点」既指卡片又指块。**建议统一为**：

- **知识点 = 笔记（Note）**，对应全局文案与"我的知识点"。
- **卡片 = 小节（KnowledgeCard）**，UI 上叫「小节」，序号化后天然成立。
- **小点 = 块（Block）**，即卡片内的一条内容。

> 命名只是文案层，不动类名（`KnowledgeCard` / `Block` 保持不变），零迁移成本。
> 顺序上**先做术语统一**再动视觉：否则新组件会在两套词汇之间反复改名。

## 2. 设计原则

1. **容器让位于内容**：能用留白、序号、心线表达的层级，就不用描边和卡片。
2. **一色一义**：一个颜色在全站只有一个含义；语义色不跟随主题强调色变化。
3. **结构性优先于文字性**：层级靠缩进/编号/连线，不靠 label 文字。
4. **按需出现**：导航设施随内容量出现与淡出（少内容时不打扰），符合"能藏则藏"。
5. **编号即锚点**：所有视觉编号（卡片 01、小点 ①②）同时是导航坐标，一物两用。
6. **文本即真相**（§3.6）：行内标记以可读语法的形式存在正文里，任何导出/导入天然承载，不存易漂移的字符 offset。
7. **不引入第三套色系**（v2 新增，重要）：_2026-09-30 重设计方案_ 第 87 行定过「不再引入第二套 accent」。
   本方案确实要引入两套新用法，因此**显式推翻该条并说明范围**：
   - 语义色（§3.2）：**不改色值**，直接**派生**自已有的 `AccentPalette`，因此不是"第二套色板"，只是给既有色值补一层语义别名；
   - 卡片身份色（§5.2）：这是**真正的第二套用法**（7 色、按卡分配）。推翻理由：区分度问题的唯一低成本解法。
     为把歧义压到最低，身份色取 `TagColors` 的低饱和批次（**不是** `AccentPalette` 的 primary，
     后者与 4 个语义角色逐值撞色）；三方分工表见 §5.2 末。
   除此之外，**不再新增任何色板**。

## 3. 关键内容的视觉强调策略（颜色编码系统）

### 3.1 强调的三个层级

强调必须**分层级**，否则处处高亮 = 没有高亮：

| 层级 | 粒度 | 表达 | 落库 | 优先级 |
| --- | --- | --- | --- | --- |
| **L1 块级** | 一整条小点 | 左缘 3dp 色条 + 块底色 8% + 块首角色标签词 | `Block.emphasis` | P2 |
| **L2 行内** | 任意字符 / 词组（**单个字也能变色**） | 文字底色 20% + 文字改用加深墨色 + 半粗 | 内联语法（在 `content` 里） | P2 |
| **L3 弱强调** | 词 | 加粗（无色） | **既有 `**文字**`**，不新增语法 | P3 |

> 关键取舍：L1 是**零富文本成本**的（只加一个枚举字段，立刻解决"关键内容无强调"）；
> L2 才需要 `AnnotatedString` 与选区处理，是本次新增的**主要技术风险点**，§3.6–3.8 专门展开。
> L3 **不新增语法**：`**粗体**` 已经由 `buildInlineLatexText` 实现并被只读渲染使用（原稿拟定的 `[[b:文字]]` 属重复建设，v2 删除）。

### 3.2 语义色板（4 个固定角色，**派生自 `AccentPalette`**）

**不复用**主题强调色这个**用法**（`AccentColor` 是用户可换的全局设置），但**复用它的色值**，不新写 hex：

| 角色 | UI 标签 | 通用含义 | 派生自 | 浅色主题（= `light.primary`） | 行内加深墨色 | 深色主题（= `dark.primary`） |
| --- | --- | --- | --- | --- | --- | --- |
| `KEY` | **要点** | 定义、结论、主旨、核心句、关键数据 | `AccentColor.OCHRE` | 赭土 `#7C5C31` | `#5E431F` | `#DCC09A` |
| `IDEA` | **想法** | 自己的理解、联想、评价、灵感 | `AccentColor.MOSS` | 苔绿 `#4B6B4F` | `#33513A` | `#AFCDB2` |
| `WARN` | **注意** | 易错、陷阱、存疑、待确认 | `AccentColor.CRIMSON` | 绛红 `#8A4550` | `#6B2C38` | `#EDB9BF` |
| `TODO` | **待办** | 跟进、延伸阅读、待补充 | `AccentColor.TEAL` | 松石 `#3D6E6B` | `#275250` | `#A5D2CF` |

**v2 的实现方式（与原稿的差别）**：

- 新增 `ui/theme/EmphasisTones.kt`，内容只做两件事：
  1. `EmphasisTone` 枚举（`KEY/IDEA/WARN/TODO`）+ 到 `AccentColor` 的映射（上表第 4 列）；
  2. 取色函数 `emphasisTone(tone, darkTheme): Color = accentRoles(tone.accent, darkTheme).primary`。
- **不新写 8 个 hex、不新增 `darkEmphasisTone()`**：`AccentPalette.kt` 里那 8 个值逐值相同（§0.5 第 6 条），
  再抄一遍等于把色值分散到两处，与 `AccentPalette.kt` 头部注释「色相取自 `TagColors`，让用户挑的强调色和标签像一家人」
  的单一来源原则冲突。
- 行内加深墨色（第 6 列）**确实需要新增 4 个常量**：它比 `light.primary` 再压一档明度，
  `AccentPalette` 里没有对应角色。放在 `EmphasisTones.kt`，注释说明「是为 14.5px 小字压的明度，不改块级标签用色」。
- 测试改为 `EmphasisTonesTest`：断言 4 个角色两两不同、映射到 4 个不同的 `AccentColor`、
  深浅两态取值分别等于 `accentRoles(...)` 的结果（**删掉 `darkEmphasisTone()` 及其测试**）。

**角色命名必须跨领域成立**：知录是**通用记录工具**，不只服务数学。
早期草案用的「定义 / 重点 / 易错」是**考试笔记**的语汇——写读书摘抄、会议纪要、生活记录时会别扭
（一段小说摘抄没有"定义"，一条菜谱没有"易错点"）。因此 UI 标签收敛为 **要点 / 想法 / 注意 / 待办**：

| 领域 | 要点 | 想法 | 注意 | 待办 |
| --- | --- | --- | --- | --- |
| 数学 | 定理、结论 | 自己的解法 | 易错点 | 待补证明 |
| 读书摘抄 | 主旨句、金句 | 读后感 | 存疑的表述 | 延伸书目 |
| 编程 | API 约定、关键坑 | 设计取舍 | 已知缺陷 | 重构项 |
| 会议 | 决议、结论 | 我的判断 | 待确认事项 | 行动项 |
| 生活 | 关键信息 | 心得 | 提醒 | 采购/跟进 |

**为什么不是更多颜色**：4 个是"一眼能记住"的上限；5 个以上用户会开始犹豫"这个该标哪个"，
标记行为一旦有决策成本就不会发生。

### 3.3 L1 表达手法（不做整块染色）

```
┌──────────────────────────────────────────┐
│ ▍ 注意  二次型正定的判定要先看顺序主子式  │   ← ▍=3dp 绛红条
│         而不能只看特征值                  │     底色 = 绛红 @ 8%
└──────────────────────────────────────────┘
```

- **左缘色条**（3dp，圆角取 `ShapeTokens.Small`）：与"页面级强调色书脊"`DocumentRow.accentSpine`
  （`DocumentRow.kt:32`）同一手法，复用已建立的语言。
- **底色 8%**：新增 `AlphaTokens.EmphasisWash = 0.08f`。
  > **v2 修正**：原稿写「新增 `AlphaTokens.Emphasis = 0.08f`」。该值与既有 `AlphaTokens.Subtle = 0.08f` 同值。
  > 同值本身可以接受（语义不同），但必须**换名 + 注释**，否则 `AlphaTokens` 头部「透明度层级的唯一来源」
  > 的定位会出现两个 0.08 让后来者无从选择。同理 §4.6 需要的 4% 应新增 `AlphaTokens.BlockFocus = 0.04f`。
- **块首标签词**：`KEY/IDEA/WARN/TODO` 四选一的小字标签，`ZhiLuType.label` 字号，用该角色色。可选显示。
- **不做**：整块文字变色（可读性差且像报错）、边框染色（与"去容器化"冲突）、图标（4 个图标更增加识别成本）。

### 3.4 L2 表达手法（字符级着色，三种笔触）

L2 解决"**单个字也要能变色以表示关键字**"。同一角色色给三种笔触：

| 笔触 | 语法 | 视觉 | 适用 | 首版 |
| --- | --- | --- | --- | --- |
| **荧光笔**（默认） | `{{k:文字}}` | 底色 20% + 加深墨色 + 半粗 | 成段的关键句 | ✅ |
| **纯变色** | `{{k-c:文字}}` | 只改文字色，无底、无内边距 | 大量高频关键字（最克制） | ✅ |
| **下划线** | `{{k-u:文字}}` | 加深墨色 + 底部 2px 同色线 | 需要"勾出"但不抢视线的词 | ✅ |

> **v2 决策（原稿与原型在此矛盾，已裁决）**：原稿 §3.4 说"首版只做荧光笔、另两种预留，
> 且笔触作为全局渲染偏好不进语法"；但原型屏 1 的图注与正文明确写「三种形态同屏共存」
> （原型 `:1164-1166`、`:1350-1352`、`:1416-1418`）。两者不可能同时成立。
> **裁决：笔触进语法、逐处指定**，理由是"全局笔触偏好"会让同一段文本在不同设置下形态不同，
> 属于渲染依赖外部状态，与原则 6「文本即真相」冲突；且原型的三形态演示本身有产品价值（同一角色可弱可强）。
> 三种笔触**自 P2 起同时交付**，不再有"预留"。

**跨领域示例**（同一套颜色，不同内容都成立）：

| 领域 | 着色后（存储形态） |
| --- | --- |
| 数学 | 二次型的标准形中 `{{i:正}}`平方项的个数由二次型本身`{{k:唯一确定}}` |
| 读书摘抄 | 这本书真正的主题是`{{i:孤独}}`，而不是爱情 |
| 编程 | `{{w:注意}}`：这个接口是`{{k:幂等}}`的，可以安全重试 |
| 会议 | 决议：`{{k:Q3 主攻海外}}`；`{{t:下周一前出预算}}` |
| 生活 | 烤箱`{{k:180 度}}`，`{{w-u:别超过 20 分钟}}` |

**单字处理（纯渲染层，不进存储）**：当被标记片段宽度 ≤ 1 个字符时，底色内边距从 2px 收窄到 3.5px 且字形加粗一档，
避免孤立单字被底色撑得突兀。是否"单字"由渲染时测量决定，**不写入数据**。

### 3.5 颜色使用规则（约束）

1. `WARN` 绛红**禁止**与 `colorScheme.error` 同时出现（避免"是警告还是报错"歧义）。
2. **一屏内 L1 标记块 ≤ 30%**；**行内着色字符数 ≤ 全文 20%**；**单块最多出现 2 种角色色**。
   超过时 UI 不阻止，但设计上不鼓励——这是防止"处处高亮 = 没有高亮"的硬约束。
3. 语义色**不**参与主题换色：换了强调色之后，`KEY` 依旧是赭土。
4. 强调是**可选**的：未标记块与未标记文字保持墨色，默认视图仍然是干净纸面。
5. **（v2 新增，v3 修订）三套颜色同源的隔离规则**。语义色、卡片身份色、主题强调色都取自
   `TagColors` / `AccentPalette` 这两个已有的色板，因此必须用"值 + 位置"两条同时隔离：
   - **值隔离（v3 已做到）**：卡片身份色取 `TagColors`，与 4 个语义角色的
     `AccentPalette.primary` **不同值**（§5.2）；这条消除了最容易出错的"身份色 = 内容色"。
   - **位置隔离**：语义色只出现在**内容区**（块级左缘条 / 行内底 / 标签词）；
     身份色只出现在**卡片 chrome**（徽标底 / 心线 / 折叠竖条）；`colorScheme.primary`
     只出现在**控件**（聚焦描边、图标、按钮）。三者不共享同一个矩形。
   - **仍存在的残余风险**：用户把主题强调色设成 `OCHRE` / `MOSS` / `CRIMSON` / `TEAL` 时，
     "标记"与"焦点/控件"会有同族色相。**必须补一条视觉检查**：这四种主题色各逐屏确认一次
     "标记"与"焦点/控件"不会被读成同一件事。此项列入 §12 验收。
   - 若真机确认歧义不可接受，退路是给 4 个语义角色改用更深/更浅一档的自定义值
     （依 `EmphasisTones` 的加深墨色思路），而**不是**新增第 5 个色系。

### 3.6 内联语法（L2 的存储格式）

**决策：不存字符 offset，改存可读的内联语法。**

理由：offset 在每次编辑（插入/删除）后都会漂移，需要全量重算，极易错位；而语法存在于文本本身，
**永远与文本同生共死**，且导出/导入/剪贴板/AI 全部零成本承载。

#### 3.6.1 语法定义（v2 定稿）

```
标记   := "\\" ("{{" | "}}")            -- 转义，输出字面量本身
        | "{{" 角色 [笔触] ":" 内容 "}}"
角色   := "k" | "i" | "w" | "t"
笔触   := ""      -- 荧光笔（默认）
        | "-c"    -- 纯变色
        | "-u"    -- 下划线
内容   := 非空，不含 "}}"、不含换行、不含 "{{"
```

| 写法 | 含义 |
| --- | --- |
| `{{k:文字}}` | 要点 KEY 荧光笔 |
| `{{i:文字}}` / `{{w:文字}}` / `{{t:文字}}` | 想法 / 注意 / 待办 |
| `{{k-c:文字}}` | 任角色 + 纯变色 |
| `{{k-u:文字}}` | 任角色 + 下划线 |
| `\{{` / `\}}` | 转义（需要字面量 `{{` / `}}` 时） |

**v2 相比原稿的三处改动及理由：**

1. **`[[ ]]` → `{{ }}`。** 原稿断言"`[[ ]]` 在自然语言中几乎不出现；唯一的现实冲突是代码"。
   **该断言已被本项目自己的产物推翻**：原型 `:1300` 就写着
   「对角线全为正但矩阵不正定：反例 `[[1, 2], [2, 1]]` 的特征值为…」——这是**数学正文里的嵌套数组**，
   不是代码块。按原稿解析规则（"`[[` 后……或直接是内容"），它会被解析成
   "把 `1, 2], [2, 1` 着色"，**静默改变正文外观**。此外 `[[...]]` 是 Obsidian/Markdown 的 wiki-link 语法，
   用户从别处粘贴笔记会高频撞上。`{{ }}` 在自然语言、数学、笔记习惯中都不成词，是更安全的载体。
2. **删掉裸写 `[[文字]]`（"使用最近一次使用的角色"）。** 这条有两个硬伤：
   - **渲染不确定**：同一段文本的角色取决于"上一次标记用了什么"，而该状态不落库、重启即失，
     同一篇笔记在不同会话渲染不同——直接违反原则 6。
   - 它正是 §3.6.1 里数学冲突的具体来源（有角色前缀的 `{{k:` 不会与 `{{1, 2}` 混淆）。
   因此**角色前缀必填**；裸 `{{文字}}` 不构成标记，原样显示。工具栏本来就由程序插入完整前缀，
   手打成本只在极少数场景出现。
3. **删掉 `[[b:文字]]`（加粗）。** `**粗体**` 已经实现且被只读渲染使用（§0.5 第 2 条），
   再加一个等价语法会产生"两种写法、两种渲染路径"，且提示词、导出、测试都要各写两遍。

#### 3.6.2 与既有行内语法的关系（v2 新增，必读）

`buildInlineLatexText`（`InlineLatex.kt:53`）已有一个 `Regex("\\*\\*(.+?)\\*\\*|`(.+?)`|\\$([^$]+?)\\$")`。
新语法**不得**另起一个平行的解析器（否则同一段文本有两条渲染路径、两套转义规则）。
做法是**把它扩成唯一的行内标记词法器**，并固定优先级：

| 优先级 | 标记 | 语义 | 备注 |
| --- | --- | --- | --- |
| 1 | `` `代码` `` | 行内代码 | **内部一律不再解析**（含 `{{`、`**`、`$`） |
| 2 | `$公式$` | 行内 LaTeX → 图片 | 既有能力，不变 |
| 3 | `**粗体**` | L3 加粗 | 既有能力，不变 |
| 4 | `{{角色:内容}}` | L2 语义着色 | 本次新增 |

- 匹配语义统一为**左起最先匹配者胜**（与现有正则的 alternation 行为一致，便于增量改造）。
- `{{...}}` 的 `内容` 内**不解析**任何其它标记（含 `$...$`）：一是避免"着色底 + 内联图片占位"
  在 Compose 中的未验证组合（`appendInlineContent` 的占位片段是否承载 `SpanStyle.background` 需实测），
  二是让解析结果可预期。**公式请写在标记之外**（`{{k:唯一确定}}$x^2$`）。此限制要写进用户可见文档。
- `CODE` 类型块与 `` ` `` 行内代码段**不解析**，因此原稿担心的"代码里 `[[nodiscard]]`"和
  "代码里 `==`"两类冲突在新语法下都不存在。

**解析容错**（对**无法识别**的写法一律原样显示，不吞字符、不报错）：
角色字母不合法、缺 `:`、内容为空、含 `}}`、跨行、未闭合、出现嵌套 `{{` —— 全部按普通字符处理。
这条是硬要求：AI 与用户都可能写错，写错**不能**造成正文缺失。

### 3.7 编辑态策略：**标记根本不进编辑缓冲**（v4 重写）

目标由评审拍板：**编辑态看不到任何标记字符**。达成它有三条路，选第三条。

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A 源码模式 | 编辑时显示 `{{k:正}}` | 一眼就是"在写代码"，与"通用记录工具"的定位不符 |
| B `VisualTransformation` + 自定义 `OffsetMapping` | 缓冲仍存带标记的全文，只在渲染时隐藏标记 | **否决**。`VisualTransformation` 只改**渲染与命中测试**，不改编辑语义：退格仍按**原坐标**删字符，光标停在内容开头按退格删掉的是 `:`。要修就得再叠一套"编辑意图修复"，而且它与中文输入法组合输入（composing）是 Compose 文本里最容易出 bug 的组合——风险全落在只有真机能验的地方 |
| **C 编辑缓冲只存可见文本（采用）** | 激活块时 `parse(content)` → `可见文本 + List<InlineSpan>`；编辑全程发生在可见文本上；每次变更由 span 表算好后 `materialize(...)` 回写 `content` | **零 offset 映射、零 IME 风险、标记物理上不可被破坏**（它不在缓冲里）。全部风险集中在两个**纯函数**上，可穷举单测 |

**C 的数据流**：

```
content（存储形态，带标记）
   ⇅  parse / materialize        ← 纯函数，性质测试：materialize(parse(t)) == t
可见文本 + List<InlineSpan>      ← 会话内派生态，从不落库
```

**这不是"offset 又回来了"**——回应 §3.6 否决 offset 的理由，区别必须说清：

- 落库的仍然是 `content` 文本，标记**跟着字符走**；span 表是**会话内派生物**，随时可从 `content` 重建，
  因此**只有一个真相**。
- offset 漂移被关在"一个编辑会话"内，由 `adjustSpans` 逐次修正；跨会话不累积。
- 一旦发现 `materialize(本地缓冲)` 与传入的 `content` 不一致（外部改动、AI 写入、撤销），
  **直接丢弃 span 表、重新 `parse`** —— 自愈发生在会话层，不在字符层。

**行为约定**：

- 只读态与编辑态的**文字外观完全一致**（都是着色文字），区别只有光标、选区与工具条。
  用户永远不会看到 `{{`。
- 编辑块不需要 `VisualTransformation`（连 `OffsetMapping.Identity` 都不需要）；只读块直接给 `AnnotatedString`。
- `**粗体**` / `` `行内代码` `` / `$公式$` **暂不进入 span 表**，保持今天的行为（源码可见）：
  代码的"说明书"就是源码本身，`$…$` 在编辑态本来就渲染不了图片。
  span 机制就位后让 `**` 也进表只是"再加一个 span 类型"的活（P3，见 §10）。
- **性能**：每次编辑 materialize 一次全文（O(n)，n = 该块字数）。常态块 < 200 字无感；
  2000 字长块需真机压测（§9.6）。
- 新动画一律走 `motionEnterTween/motionExitTween` 并读 `LocalReducedMotion`（`Motion.kt:59-90`），
  不要新写 `tween(240)` 字面量。

**必须防的两个已知坑**（同时写进 §11 风险表）：

1. **外部同步导致光标跳动**：`onValueChange` 回写 `content` 后，`content` 又会作为参数回到编辑器。
   若编辑器每次无条件 `parse(content)` 重建本地状态，光标与输入法会被重置。
   做法：本地持有 `(可见文本, spans)`，**只在传入的 `content != materialize(本地)` 时才重新 `parse`**。
   这是受控/非受控文本组件的经典坑，必须真机验证"连续打字不丢字、光标不跳"。
2. **边界输入语义必须显式定义**（见 §3.11.2 规则表），否则"在标记末尾继续打字"这类高频动作会时对时错。

### 3.8 划词起色的交互（v4 更新：以 span 为操作对象）

```
         ┌──────────────────────────────┐
         │ ● ● ● ●  │  B  U  ✕   ▾     │   ← 浮动工具条（选区上方 8dp）
         └──────────────────────────────┘
   二次型的标准形中 正 平方项与负平方项…
                    └ 选中单个字也成立
```

- **触发**：编辑态拖动选区（或长按选字）→ 抬手上浮工具条（复用 Android 文本选择工具条位次）。
  只读态的长按仍然只给"复制此块 / 引用到 AI"菜单（`ReadOnlyBlock.kt:33-131`），不参与标记。
- **内容**：4 个角色色块 + `B`（加粗，直接写既有 `**`）+ `U`（下划线，即 `-u` 笔触）+ `✕`（清除格式）+ `▾`（更多）。
- **操作对象是 span，不是字符串**：点色块 = 给选区加/改一个 `InlineSpan`；
  只有回写 `content` 时才由 `materialize` 物化成 `{{...}}`（§3.11.2）。
  因此"切换/取消"不涉及全文搜索替换，也**不可能命中相邻的同角色标记**。
- **点已标记文字 / 光标落在标记内**：工具条**自动高亮当前角色与笔触**——
  这是用户"看得见格式"的唯一入口，必须有（否则用户不知道为什么这段有底色）。
- **工具条三种状态**：

  | 状态 | 触发 | 工具条表现 |
  | --- | --- | --- |
  | 未标记 · 有选区 | 选中普通文字 | 4 个色块都不选中 |
  | 光标在标记内 | 点已标记文字 | 对应色块 + 笔触项选中；`✕` 可用 |
  | **标记中** | **没有选区时点色块** | 色块选中 + 显示「标记中」旗标；**之后输入的文字自动落入该标记**（零长 span 扩展，§3.11.2）；再点该色块 / 失焦 / 点别处结束 |

- **「标记中」的结束语义**：结束时若 span 仍为零长 → **丢弃**（不留空标记）；
  若已有文字 → 固定下来，其文本形态就是 `{{角色:已输入的文字}}`。
- **键盘可用**：底部工具栏（`KnowledgeBottomToolbar`，由 6 槽位增至 7：Aa / **标记** / 图片 / ∑ / `</>` / 链接 / 分支）
  增加「标记」入口，选中文字后点它也能起色（无需长按）。
  该行已按 `activeCardId != null` 整体置灰（`KnowledgeBottomToolbar.kt:46-123`），新区块沿用同一门控。
- 标记动作最终仍**是一次内容变更**，因此自动保存（500ms 防抖）、`setDragging` 的延迟保存等既有机制无需改动。

### 3.9 无障碍（行内着色的固有短板）

行内着色的信息载体**只有颜色**，对色觉障碍用户不友好。缓解措施：

1. 行内标记**同时**用 `font-weight: 600`（半粗）+ 底色（不只靠色相）——明度差在灰度下依然可辨。
2. 语义角色提供 `contentDescription`（如"要点标记：正定"），TalkBack 可读。
   > 现状提醒：`AddKnowledgeCardButton` 的 `Icons.Default.Add` **`contentDescription` 为 null**（`AddKnowledgeCardButton.kt:24-60`），
   > 顺手补上。
3. 「设置 → 无障碍」提供**色盲友好色板**开关（换成明度差更大的 4 色），与主题色解耦。

### 3.10 `Block.content` 的所有读取方（v2 新增，原稿最大漏项）

语法活在 `content` 里，意味着**每一处读 `content` 的地方都会被语法字符影响**。
原稿只列了"摘要"和"页内查找"，实际有 **11 处**，必须逐条给结论：

| # | 读取方 | 证据 | 是否剥离语法 | 结论 / 工作量 |
| --- | --- | --- | --- | --- |
| 1 | 只读 TEXT 渲染 | `BlockContent.kt:55-60` → `RichText` | 渲染（不剥离，解析） | 本次改造的主战场 |

### 3.11 语法的防手写与防破坏（v4 新增）

**原则：内联语法是存储格式，不是交互。** 用户永远不需要打出 `{{`，也不会看到它 ——
像 HTML / LaTeX 一样，没人手打标签。

#### 3.11.1 用户意图 → 零输入操作

| 用户意图 | 操作 | 打字 |
| --- | --- | --- |
| 给几个字起色 | 选中 → 浮动工具条点色块 | 否 |
| 起色（不想长按） | 选中 → 底部「标记」→ 点色块 | 否 |
| 改色 / 换笔触 | 光标放进已标记文字 → 工具条**自动高亮当前角色与笔触** → 点别的 | 否 |
| 取消标记 | 同上 → 点 `✕` | 否 |
| 没选字就想用某个色 | 点色块 → 进入「**标记中**」态（§3.8），之后输入自动带上 | 否 |
| 整条小点标角色 | gutter 圆点 → 4 色 | 否 |

**"最近角色"的正确用法**（澄清 §3.6.1 的修正）：砍掉裸写 `{{文字}}`，是因为**解析时**依赖"最近角色"
会让同一段文本在不同会话渲染不同。但"最近角色"作为**插入时的默认值**完全没问题 ——
角色一旦被插进文本就被冻结，渲染依然确定。所以工具条可以记住上次用的角色并默认选中，
用户在 90% 的场景里仍然只需一个动作。

#### 3.11.2 span 变换规则（`adjustSpans`，纯函数，穷举单测）

`List<InlineSpan>` 用**可见文本坐标**表示。每次编辑由 `(可见文本, 选区, 替换内容)` 推出新的 span 表：

| 编辑动作 | span 处理 | 理由 |
| --- | --- | --- |
| 在 span **内部**插入 | `end += 插入长度` | 明显 |
| 在 span **末尾**插入（caret == end） | **扩展** | "我在接着写这个要点"——高频意图 |
| 在 span **起始**插入（caret == start） | **不扩展** | "新写的字不属于这个标记" |
| 删除与 span 相交 | 按交叠长度**收缩** | |
| 删除完全覆盖 span | **删除该 span**，文字按用户选择删 | 意图明确 |
| **零长 span**（「标记中」）处的输入 | **扩展** | 「标记中」就靠这个实现：在光标处放一个零长 span，随后输入自动落入 |
| 粘贴 / 输入含 `\n` | span 在换行处**断开**（不跨行） | 内联标记不跨行（§3.6.1） |
| 全选删除 | span 全清 | |

**零长 span 的生命周期**：点色块创建 → 输入即扩展成形 → 失焦或点别处时若仍为零长则**丢弃**（不留空标记）。

#### 3.11.3 编辑器之外的入口仍要兜底（`InlineMarkupNormalizer`）

span 机制保证"用户在编辑器里写不坏"，但还有三个入口是**文本直接进来**的，必须过一遍规范化：

| 入口 | 处理 |
| --- | --- |
| 系统剪贴板粘贴纯文本 | 先 `normalize(粘贴内容)` 再插入（未闭合 / 角色非法 → 去掉标记、保留文字） |
| AI 工具写入（`create_note` / `update_note`） | 落库前 `normalize`。模型写错只损失标记，不污染正文（§9.4） |
| 历史数据 / `.dtk` 导入 | **不主动改写**（解析器本就容错）；该块一旦被编辑，第一次 `parse` + `materialize` 会顺带规整 |

`normalize` 与 §3.6.2 的"原样显示"是互补的两件事：**解析器负责"读得安全"，normalize 负责"写得规整"**。

| 输入 | 输出 |
| --- | --- |
| `{{k:文字`（未闭合） | `文字` |
| `文字}}`（孤立闭合） | `文字` |
| `{{x:文字}}`（角色非法） | `文字` |
| `{{k:}}`（空内容） | （整段移除） |
| `{{k:a{{i:b}}c}}`（嵌套） | 内层优先，外层降级为文字 |
| `{{k:abc` + 换行 + `def}}` | `{{k:abc}}\ndef`（断开，不自动续开） |

**唯一验收标准：最坏情况是标记掉了、文字还在。** 用户重新标一次即可。

#### 3.11.4 手打辅助（P3，可选）

给外接键盘 / 极客用户：打 `{{` 自动补成 `{{最近角色:}}` 并把光标放中间；打 `{{k` 弹角色提示。
中文输入法下 `{` `}` 在符号页，所以这**不是**主路径，只是兜底。

#### 3.11.5 测试点（全部纯函数，无需真机）

- **性质测试**：`materialize(parse(t)) == t`（对随机生成的合法 `t`）；
- `adjustSpans` 的 8 条规则逐条覆盖，重点是**边界插入**、**零长 span**、**跨行断开**；
- `normalize` 的 6 条规则；
- `parse` 对 §12 列出的全部"不会被误解析"用例。

## 4. 知识点内部：小点的结构化呈现

### 4.1 结构化行取代「块卡片」

**核心改动：块不再有常态描边**。静态阅读时，块的边界由三样东西表达，而不是框：

```
       gutter(28dp)          内容区
      ┌────┬─────────────────────────────────┐
  01  │ ①  │ 二次型 f(x)=xᵀAx …              │  ← 小点序号
      │ ┃  │                                 │
  02  │ ②  │ ▍注意  只判顺序主子式不够        │  ← 已标记小点
      │ ┃  │                                 │
  03  │ ③  │ ┌ f(x) = Σ λᵢyᵢ² ┐               │  ← 公式块（居中的微凹纸底）
      │ ┃  │                                 │
  04  │ ▾  │ 〈分支：三种情形〉        (3)     │  ← 分支块，带子点数
      │ ┃  │   1.1 情形一 …                  │  ← 子块用二级编号 + 加深缩进
      │ ┃  │   1.2 情形二 …                  │
      └────┴─────────────────────────────────┘
        ┃ = 连续心线（同属本卡片的块串成一条竖线）
```

### 4.2 小点编号（序号即坐标）

- 顶层小点：`①②③…`（超过 20 用 `㉑` 或回落为数字），`ZhiLuType.meta` 字号，强调色 40% 透明度。
- 分支子块：`1.1 / 1.2 / 2.1`（父序号.子序号），`meta` 字号，`onSurfaceVariant` 灰。
- **纯视觉派生**：由列表索引即时计算（`sortOrder` 在保存时已被重排为全局序号，见 §0.5），**不落库**。
  拖拽排序后编号自动重排，零成本。
- 编号同时被目录（§6.1）与索引轨（§6.2）复用为坐标。

### 4.3 层级与「心线」

- 顶层块 gutter 缩进 0，分支子块额外缩进 24dp（沿用现有 `BranchContentIndent = 24.dp`，`BranchBlockContent.kt:47`）。
- **心线（spine）**：在 gutter 右缘画一条 1dp 竖线贯穿整张卡片的块序列，颜色 = 卡片强调色 @ 26%。
  - 作用：把"一列互不相干的块"变成"一棵有根的树"，这是解决"结构不清晰"最关键的一笔。
  - 分支块处心线**分叉**一段短线指向子块，强化从属关系。
- 分支折叠时，心线在该处收束为一个 `▾` 节点，展开后延伸。
- 心线透明度需真机校准：太深喧宾夺主，太浅串不起结构。

### 4.4 类型可视化（常显，不依赖激活态）

| 类型 | 静态表达 | 编辑态附加 |

## 5. 知识点之间的区分与标识

### 5.1 卡片序号徽标

```
┌─────────────────────────────────────────────┐
│  ┌────┐                                     │
│  │ 01 │  惯性定理与规范形          ▾   (5)  │  ← 序号徽标 + 衬线标题 + 折叠 + 小点数
│  └────┘  用正交变换把二次型化为标准形…       │  ← 摘要行（自动取首个小点首句）
│  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬       │  ← 心线色 = 卡片强调色
│  ①  内容…                                    │
└─────────────────────────────────────────────┘
```

- 序号：衬线体、2 位补零（`01`~`99`），`ZhiLuType.cardTitle` 字号，颜色 = 卡片强调色。
- 徽标底色：卡片强调色 @ 10%，圆角 `ShapeTokens.Small`，尺寸 34×34dp。
- **价值**：这是"知识点之间区分度"最主要的手段，同时兼任目录锚点与索引轨标签。
- 序号徽标**替代**现在的 `📌 PushPin`（`CardHeader.kt:47-52`）。图钉的
  `contentDescription = "知识小点"` 一并按 §1.3 改为「小节 1」这类可读文本。

### 5.2 卡片强调色（显式轮转序、用户可改）

- **色源：`TagColors` 的低饱和批次**（`Color.kt:71-79`，与标签胶囊同一套值），
  **不是** `AccentColor` / `AccentPalette` 的 primary。
  **v3 修正的理由（这一条是做原型时发现并回填的）**：`AccentPalette` 的 4 个 `light.primary`
  —— 赭土 `#7C5C31`、苔绿 `#4B6B4F`、绛红 `#8A4550`、松石 `#3D6E6B` ——
  与 §3.2 的 4 个语义角色**逐值完全相同**。若卡片身份色也用这批值，
  "卡片 02 的心线"与"这张卡里某条小点的 `KEY` 标记"就是同一个颜色，直接违反原则 2「一色一义」。
  `TagColors` 是同一色相家族的低饱和版本：既不与语义色撞值，又与标签胶囊一致，
  而且"身份色比内容色更淡"正好符合原则 1「容器让位于内容」。
- **这是本方案显式推翻 _2026-09-30 重设计方案_ 第 87 行「不再引入第二套 accent」的地方**（理由见 §2.7）。
  影响面：该文档同处规定「所有强调（高亮、焦点、选中）统一由主色/三级色派生」——本方案新增的
  「卡片身份色」超出该范围；主题强调色本身的行为不变（仍由设置页控制，`Theme.kt:134-142` 只覆盖 primary 族）。

**默认值：显式轮转序，不用取模公式。**（v2 修改）

原稿写 `f(cardIndex) = (cardIndex × 3) % 7`，理由是"步长 3 与 7 互质，相邻卡片色相拉得更开"。
按色板的真实顺序代入该公式，前 4 张卡是 **墨蓝 → 苔绿 → 石墨 → 松石**，其中「苔绿→石墨」「石墨→松石」
都落在低饱和绿青灰区间，**相邻卡片几乎分不出来**——恰好没达成它自己的目标。
原因是这批色并非均布色轮，而是"成对相邻"的作者色（蓝紫 / 青绿 / 赭红 + 中性），
任何固定取模都会周期性撞进同一色族。

改为**显式有序表**（`CardAccentRotation`，放 `ui/theme/AccentPalette.kt` 或新文件）：

```
墨蓝 #4A5C7A → 赭土 #8A6B3A → 松石 #4A7A7A → 绛红 #8A4A5B → 苔绿 #4A6B5B → 石墨 #6B6B6B → 黛紫 #6B5B8A → (回到墨蓝)
```

前 5 张卡 = 蓝 / 赭 / 青 / 红 / 绿，五个不同色族——覆盖绝大多数笔记的卡片数。
配一条单测：断言前 5 项两两色相不同族、且相邻项明度差 ≥ 阈值；**不要**断言公式性质。

- **用户可改**：长按卡片头 → 色板弹窗（**与标签色板同一个组件、同一批值**）。
- **作用范围仅三处**：序号徽标底色（`TagColors` 值 @ 12%）、心线颜色（@ 26%）、折叠态左侧 3dp 竖条。
  **不做整卡染色**，纸面保持干净。
- **三方分工表（"一色一义"的落实）**：

  | 用途 | 来源 | 出现位置 |
  | --- | --- | --- |
  | 语义角色（内容） | `AccentPalette.primary` | 行内底色 20%、块级左缘 3dp 条、角色标签词 |
  | 卡片身份（容器） | `TagColors` | 序号徽标底色 12%、心线 26%、折叠竖条 |
  | 主题强调色（控件） | `AccentColor`（用户可在设置里换） | 聚焦描边、按钮、图标 |

  三者色相同族、**值不同、位置不同**；身份色与主题色**互不联动**——卡片色不随主题色变化、也不回写主题。
  默认值只在**卡片创建时**写入一次（见 §9.1 的 `accent` 列），此后不再重算。
  设置页的强调色选择器文案应标注「界面强调色」，与卡片色板区分。

### 5.3 标题层级 + 摘要行

- 卡片标题：`ZhiLuType.cardTitle`，**17 → 18sp**，衬线，与正文 `body 16sp` 拉开。
- 摘要行：`meta` 字号，`onSurfaceVariant` 灰，取卡内第一段有内容的 TEXT 首句，截断 1 行。
  - 摘要需**先剥离内联语法**再截断（§3.10 第 3 条），否则摘要里会出现 `{{`。
  - **v2 订正**：原稿说"复用已有逻辑：`NoteViewModel` 里'标题为空时退回块摘要'的实现可直接抽取"。
    实际 `NoteViewModel.cardLabel`（:876-883）**只服务 AI 引用的标签**，UI 的空白标题回退是一个字面量
    `"知识小点"`（`CardHeader.kt:56`）。所以摘要行是**新写的纯函数**（建议放 `ui/home/NotePreview.kt` 旁或
    `ui/note/knowledge/`，与 `notePreviewText` 共用剥离逻辑），并顺手让 `cardLabel` 复用同一实现。
- 卡片聚焦/编辑时摘要行隐藏（不占位，避免抖动）。

### 5.4 折叠态（扫描视图）

- 卡片头右侧 `▾` 箭头，点击折叠整卡 → 只留 `序号徽标 + 标题 + 摘要 + (小点数)`。
- 折叠态高度约 64dp，一屏可扫 8~10 个小节。
- 顶部栏提供"全部折叠 / 全部展开"（长按折叠箭头触发，避免常态多一个按钮）。
- **与索引轨、目录联动**：折叠态是索引轨的最佳搭档（骨架视图 + 刻度跳转）。
- **v2 说明**：这是**全新功能**。`KnowledgeCard.isExpanded` 目前是死字段（§0.5 第 8 条），
  要么启用它、要么删除它——不要留着一个"看起来管折叠"但没人读的字段（这正是当初 `isExpanded` 变成死字段的原因）。
  折叠状态**会话内 `remember`**，与 `branchExpandedStates` 的现有做法一致（`NoteUiState.kt:39`，不落库）。

### 5.5 卡片容器

- 卡片仍是 `surface` 白底 + `shapes.medium`（= `Radius.Card` 14dp），但**去掉常态描边**，只保留阴影；
  聚焦态才出现 2dp 强调色描边（现状保留）。
- **v2 提醒（token 共享）**：静息规格来自 `AppCardStyle`（`borderWidth = 1.dp`, `elevation = ElevationTokens.Card = 0.dp`），
  而该对象**被「新增卡片」按钮共用**（`AddKnowledgeCardButton.kt`，`AppCard.kt:21-25`）。
  因此"去掉常态描边 + 加 `ElevationTokens.Raised` 阴影"不能直接改 `AppCardStyle`——
  否则按钮也会一起变形。做法：知识卡改用自己的局部规格（或给 `AppCardStyle` 拆成 `card` / `button` 两组），
  并明确 `ElevationTokens.Card = 0.dp` 这个"靠聚焦边框分层、不用阴影"的既有决定**只对知识卡失效**，注释要跟着改。
- 卡片之间：`Spacing.SectionGap = 28dp` 留白 + 一条 `ZhiLuDivider`（起始缩进 = `PageGutter`）。
- 效果：整页读起来像"一篇有章节的文档"，而不是"一叠卡片"。

## 6. 内容导航与定位

三层设施**按内容量递进出现**，任何一层都不会在内容少时打扰用户。

### 6.1 页内目录（Outline Sheet）

- 入口：顶部栏「目录」图标；**仅当卡片数 ≥ 3** 时出现在 `NoteTopBar`。
  `NoteTopBar`（`NoteTopBar.kt:46-75`）现在只有返回 + 保存/分享/编辑，新增图标要处理
  **浏览态/编辑态两套 actions** 的排布（编辑态已有一个主色 ✓，浏览态有 `ReviewPill` + 分享 + 编辑）。
- 形态：底部 sheet（复用 `ShareFormatBottomSheet` 的形态），列出：
  ```
  ┌ 目录 ────────────────────────┐
  │ 01  惯性定理与规范形      5  │  ← 序号(卡片色) · 标题 · 小点数
  │ 02  合同变换的性质        3  │
  │ 03  正定矩阵的判定        7  │  ← 当前所在（左缘卡片色竖条 + 底色 6%）
  └──────────────────────────────┘
  ```
- 交互：点击 → `listState.animateScrollToItem(卡片序号 + 1)`，落地后该卡片头**闪烁一次**
  （边框 2 帧强调色淡出，走 `MotionDuration.Medium` 且尊重 `LocalReducedMotion`）。
  **+1 是必须的**：列表第 0 项是标题头（无 key 的 `item`），卡片从第 1 项开始
  （`NoteEditScreen.kt:251-274`）；现有"加卡后自动滚动"已经踩过这个偏移（同文件 `:98-104` 的
  `lastIndex = cards.size + 1`）。
- **当前项高亮**：由 `LazyListState.firstVisibleItemIndex` 反查卡片序号推导，随滚动实时更新。

### 6.2 右缘索引轨（Index Rail）

这是解决"小点多时定位困难"的主力，也是纸墨风里最不打扰的形态。

```
                        ┌─┐
                        │▬│ ← 刻度 = 一张卡片
                        │▬│   长度 ∝ 小点数
                   ┌─┐  │▬│   颜色 = 卡片强调色
                   │─│  │▬│
                   │─│  │▬│ ← 当前可视卡片：加粗 + 加长
                   │─│  │▬│
                   └─┘  │▬│
                        └─┘
```

- 位置：页面右缘，距边 8dp，垂直居中，宽 16dp（命中区 ≤ 24dp = `Spacing.GutterTap`，避免与列表滚动手势冲突）。
- 每个刻度：宽 3dp（当前 5dp）、高 12dp（长卡 16dp）、间距 4dp、圆角 2dp、颜色 = 卡片强调色 @ 55%。
- **拖动 scrub**：按住上下拖动，实时 `scrollToItem`，并浮现一个气泡显示 `01 惯性定理与规范形`
  （复用目录条的紧凑形态）。
- **出现条件**：卡片数 ≥ 4 **且** 内容高度 > 1.5 屏；滚动时淡入，**静置 2 秒后淡出**。
- 点按某个刻度 = 直接跳转该卡片（不拖动也能用）。

### 6.3 Sticky 卡头

- 长笔记滚动时，让**当前卡片的头部**吸附在顶部栏下方，形成一个始终可见的"我在第几章"提示条。
- 实现一致性：`HomeNoteList` 已用 `stickyHeader`（`HomeNoteList.kt:45`），此处沿用同一 API 与视觉
  （白底 + 底部发丝线 + 序号）。
- 折叠态卡片天然就是 sticky 条，无需额外实现。

### 6.4 页内查找（P3）

- 顶部栏「查找」→ 输入关键词 → 命中块高亮（复用 `NoteRow.highlightMatches` 的着色逻辑，
  `NoteRow.kt:186-206`，注意它是**不可组合**的纯函数、`highlightColor` 无默认值）+ 上下箭头跳转。
- **与行内标记的叠加**：查找命中用「主色描边/底色」；与行内语义色同时出现时，以查找高亮优先（临时态压过持久态）。
- 查找匹配需**先剥离内联语法**再匹配（§3.10 第 4 条）。

### 6.5 三层设施的联动

| 触发 | 目录 | 索引轨 | sticky 卡头 |
| --- | --- | --- | --- |
| 滚动 | 当前项高亮同步 | 当前刻度加粗 | 内容更新 |
| 点目录项 | — | 刻度跟随 | 更新 |
| 拖索引轨 | 若打开则同步高亮 | 气泡显示标题 | 更新 |

统一由 `LazyListState.firstVisibleItemIndex` 单一数据源驱动，避免三套状态各自漂移。
**索引项 → item index 的换算集中到一个函数**（`cardIndex + 1`），三个设施共用。

### 6.6 LazyColumn 结构的现实约束（v2 新增，影响 §6.1–6.3 的可行性）

现状（`NoteEditScreen.kt:245-383`）：`LazyColumn` 的第 0 项是标题头，其后**每张卡片一个 item**（`key = card.id`），
**卡内的块是 `CardBlockList` 里的普通 `Column`，不是 lazy item**（`CardBlockList.kt:109-120`）。
由此推出四条会影响本方案的结论：

1. **目录跳转可行**：`animateScrollToItem(cardIndex + 1)` 精确命中卡片顶部。
2. **索引轨的刻度粒度只能是"卡片"**：正好与 §6.2 的设计一致（一个刻度 = 一张卡），无需改结构。
3. **sticky 只能吸附到卡片级**：`stickyHeader` 需要 item 边界；想做到"当前小点的编号/类型吸附"
   必须先把卡片摊平为 item 流（卡片头、每个块各成 item）。**本方案不摊平**，sticky 卡头仅到卡片粒度，
   §6.3 的措辞按此收窄。
4. **大卡首帧成本**：一张有 30 个块的卡会一次性组合全部块（非 lazy）。
   加上行内解析（§8）后，单卡成本上升。对策：`AnnotatedString` 按 `content` 做 `remember` 缓存（§8），
   并在 §11 记为风险项；若真机出现卡顿，再单独立项做"扁平化 + 块级 lazy"重构，
   **不要**把它塞进本方案的某一期里。

## 9. 数据与兼容性影响

### 9.1 需要落库的字段（一次 v5 → v6 迁移）

| 字段 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `accent` | `KnowledgeCard` / `NoteCardEntity` | **`Int?`（null = 未设置）** | 卡片身份色，存 `TagColors` 的色值（与 `TagEntity.color` 同一约定）；默认由创建位置按 `CardAccentRotation` 写入 |
| `emphasis` | `Block` / `NoteBlockEntity` | `Int`（0=无，1=KEY，2=IDEA，3=WARN，4=TODO） | 块级语义标记 |

**三条必须遵守的实现细节（v2 新增，原稿缺失，缺一条就过不了验证）：**

1. **`accent` 用可空 + `null` 表示"未设置"，不要用 `0` 或任何合法色值当哨兵。**
   原稿写"`accent` 默认 0 → 读取时若为 0 则按索引回退轮转"。
   `0` 是 `Color(0x00000000)`（全透明黑）——只要将来有人把 `0` 当成一个合法色值，语义立刻崩；
   更要紧的是"用户显式选了这个色"与"还没设置"必须可区分，否则用户的选择会被轮转静默覆盖。
   约定：
   - `accent INTEGER`（可空）：`null` = 未设置 → 渲染时按 `CardAccentRotation[cardIndex]` 取色（**不写库**）；
     非空 = 用户显式选择，永远优先。
   - 存储形态与既有 `TagEntity.color: Int`（`TagEntity.kt:15`）一致，因此**不需要**引入
     `AccentColor.name` 那套字符串约定——那是 DataStore 的做法（`UserPreferences.kt:36-40`），不是 Room 的。
   - 若将来确要存 ordinal，必须另配哨兵（如 `-1`）并写进注释。
2. **Room 的 `defaultValue` 必须与迁移 DDL 完全一致。**
   实体上加 `@ColumnInfo(defaultValue = "0")`（`emphasis`）与 `@ColumnInfo(defaultValue = "NULL")`（`accent`，可空可省），
   迁移里写 `ALTER TABLE note_blocks ADD COLUMN emphasis INTEGER NOT NULL DEFAULT 0`。
   `MigrationTest` 用 `runMigrationsAndValidate` **逐字比对导出 schema**，一边有 `DEFAULT`、另一边没有就会失败。
   （现状 `app/schemas/…/5.json` 里"没有任何 defaultValue"，所以这是本项目第一次踩这个点。）
3. **`emphasis` 必须贯穿"内存块 ↔ 落库块"的全部转换点**，否则每次保存静默清零：
   - `ui/note/NoteUiState.kt` 的 `toNote()`（:57-64，按 `cardIndex * 10_000 + blockIndex` 摊平）；
   - `NoteViewModel.blocksForState`（:1037-1038，`sortOrder = index`）与 `syncBlocksToState`（:1022-1035）；
   - `data/local/mapper/BlockMapper.kt`（双向）、`NoteRepositoryImpl.replaceBlocks`（:155-193）；
   - 所有 `Block(...)` 构造点（`Block` 是 data class，新增字段有默认值，编译器**不会**报错提示漏传——
     这正是姊妹文档《2026-10-02 笔记内容丢失…》那一类 bug 的成因，必须靠测试兜住）。

**其余迁移要求**：
- 写 `Migration(5, 6)` 并挂到 `Migration.all`（`Migration.kt:81`）；**禁止** `fallbackToDestructiveMigration()`。
- 导出 schema `6.json` 需提交版本控制；`MigrationTest` 补 `migrate5To6` 用例
  （现有测试只覆盖 `MIGRATION_2_3` / `MIGRATION_4_5`，`1_2` / `3_4` 从未被测——新用例请照 `migrate4To5` 的写法：
  `createDatabase(db, 5)` + 插一行旧数据 + `runMigrationsAndValidate(db, 6, true, MIGRATION_5_6)` + 读回断言默认值）。
- **行内着色不新增字段**：它活在 `Block.content` 文本里（§3.6），因此**无需迁移**。
- 顺手订正 `AGENTS.md`：版本号 4 → 6，并补 `note_cards.accent` / `note_blocks.emphasis` 的说明。

### 9.3 导出 / 导入承载（必答题，且原稿结论有错）

**先纠正两个事实（§0.5 相关）：**

- **`.dtk` 的 `note.json` 里根本没有 `dtkVersion` 键。** 导出只写 `"version":1`
  （`JsonExporter.kt:29`；`DtkExporter.kt:47-51` 复用同一 writer）；导入端读 `dtkVersion`，缺省当 1
  （`ImportKnowledgeUseCase.kt:63-66`）。所以"`dtkVersion` 不升"这句话在现状下是空转——
  要升版本，**得先把它写出来**。`AGENTS.md` 与 `2026-07-12-share-and-import-design.md:60` 都误以为它已经写了。
- **JSON / `.dtk` 不导出卡片**：`JsonExporter` 只写 note + `contentBlocks` + tags（`:63-80`），
  `DtkExporter` 把卡片 `flatMap` 成块（`:30-33`）。因此**卡片级字段 `accent` 无法往返**。

| 格式 | 处理 |
| --- | --- |
| JSON | `content` 原样保留语法（内部备份语义，导入可还原）；`emphasis` 随块往返 ✅；**`accent` 丢失** ⚠️ |
| **Markdown** | 需新增转换：`{{k:文字}}` → `<span style="color:#5E431F;background:#7C5C3121">文字</span>`（Markdown 标准不支持着色，用内联 HTML）。`MarkdownExporter.kt:95` 现在对 TEXT **完全不做转义/转换**（唯一转义只用于 LINK 标题，`:146-156`），这是新增逻辑 |
| **HTML** | 同上，转成内联 `span`。`HtmlExporter.kt:63-70` 现在只做 HTML 转义 + `\n\n`→`<p>` + `\n`→`<br>` |
| `.dtk` | `note.json` 原样保留语法；`emphasis` 随块往返 ✅；`accent` 丢失 ⚠️ |
| 行内代码 / CODE 块内 | **不解析**语法（§3.6.2），导出时原样保留 |

**关于 `accent` 丢失的决策（建议"接受"）**：
卡片色的默认值本身就是 `CardAccentRotation[cardIndex]`（§5.2）。导入一份丢失 `accent` 的备份后，
所有卡片的 `accent` 为 `null` → 一律落到轮转默认值 → **外观合理**。
因此**不必**为了这一字段去扩 JSON 结构、抬 `dtkVersion`；但要：
- 在 `docs` 与设置页的备份说明里写明"卡片自定义强调色不随 JSON/.dtk 备份"；
- 在 §12 验收里加一条"导出再导入后，卡片色回到默认轮转而不是全灰"。
- 若将来确实要让 `accent` 往返，正确做法是给 `JsonExporter` 增加 `cards` 数组并抬 `dtkVersion` 到 2
  （导入端 `> 1` 会拒绝，所以这必然是一次破坏性变更，需要单独评估）。

- 需要同步改动 `MarkdownExporter` / `HtmlExporter`，并在导出器测试里覆盖"带标记文本"用例
  （现有 6 个导出/导入测试，**没有任何一个**涉及行内标记，见 §附）。
- **现状遗留**：导出器不认既有的 `**`/`` ` ``/`$`，所以 Markdown/HTML 里的 `**粗体**` 目前是原样输出、
  `$公式$` 是原样输出（`$` 在 Markdown 里通常还被当作公式定界符）。本次改造应**一并**把三种既有标记也转成
  Markdown/HTML 语义（`**` → `**`、`` ` `` → `` ` ``、`$` → `$` 或 base64 图），否则新增的 `{{ }}` 转换会显得孤立。

### 9.4 AI 与剪贴板

- **先修一个既有矛盾**（§0.5 第 4 条）：系统提示词（`AiAssistantRepositoryImpl.kt:169-172`）告诉模型
  「笔记正文不渲染 Markdown 标记，行内 `**加粗**` 都会原样显示，请一律改用纯文本」，
  但只读渲染**确实会**渲染 `**加粗**`。这条提示词需要按事实改写。
- **AI function calling**：写块内容的工具是 `create_note` / `update_note`（`AiToolExecutor.kt:42-122`），
  非图片块的 `content` **逐字写入**（`:246-258`）。**必须在系统提示里声明内联语法**，
  使 AI 也能主动标记关键字；解析器对**非法写法原样显示**（§3.6.2 容错），
  因此即使模型用错语法也不会污染数据。建议在提示词里给 3~5 个正例与 3 个反例（含"公式写在标记外"）。
- **块剪贴板**：`BlockClipboardSerializer` 的 DTO 是 `version/type/content/language/children`
  （`BlockClipboardSerializer.kt:23-30`，原稿写的 `BlockClipboardData` 是错的），`content` 原文存储，
  **自动承载**语法，粘贴后即刻渲染。无需改动。
- **AI 读取上下文**：`AiToolExecutor.formatNote`（:340-359）与 `AiTaskManager.formatBlock`（:274-283）
  把块内容喂给模型前，**保留语法**（让模型知道哪些是关键），但在提示里说明含义。
  另需修 `AiToolExecutor.snippetOf`（:361-366）：它 `take(60)` 直接截断，语法字符会挤占摘要预算，
  建议先 `stripMarkup` 再截断（§3.10 第 10 条）。

### 9.5 不涉及的

- `BlockType.value` 稳定值不动。
- 不做完全 WYSIWYG 富文本编辑器：§3.7 的"编辑缓冲只存可见文本 + span 表"是**最小必需**的机制，
  不做选区样式继承、不做嵌套样式、不做表格/列表。
- 不做"卡片摊平 + 块级 lazy"重构（见 §6.6 第 4 条，单独立项）。

### 9.6 性能

- 行内解析开销：`AnnotatedString` 按 `content` 做 `remember(content)` 缓存，滚动时不重复解析
  （`RichText.kt:39` 已是此写法，扩解析器时保持）。
- 只读块走"解析 → `AnnotatedString`"；**编辑块不需要 `VisualTransformation`**，
  但每次编辑都要 `adjustSpans` + `materialize` 一次全文（都是 O(n)，n = 该块可见字数）。
  常态块 < 200 字无感；**2000 字长块需真机压测连续输入**（§11 风险项）。
- `materialize` 的结果就是 `onValueChange` 的上行值，所以自动保存路径上不会有额外的一次全文扫描。
- `LazyColumn` 按卡片懒加载，但**卡内块不懒**（§6.6 第 4 条）。大卡（>20 块）需真机测首帧，
  必要时先做"卡内块分页/延迟组合"的轻量优化，再考虑扁平化。

## 12. 验收口径

- **可读性**：5 张卡 × 6 小点的笔记，同屏可辨认"当前在第几章、第几小点"。
- **定位**：从第 1 张卡跳到第 5 张卡 ≤ 1 次操作（索引轨点按）；目录点击落到卡片顶部（含 `+1` 偏移）。
- **强调 · 块级**：任意小点可 2 步内完成语义标记；未标记块视觉上与现状一致。
- **强调 · 行内（零输入）**：任意单字可在 2 步内着色（选字 → 点色），**全程不需要输入任何标记字符**；
  三种笔触都能写入并正确还原；没有选区时点色块可进入「标记中」，随后输入的文字自动带上该角色。
- **标记不可见**：编辑态与只读态**都看不到 `{{`**（编辑态缓冲里根本没有标记）；
  光标落进已标记文字时，工具条高亮当前角色与笔触。
- **标记不可破坏**：在标记内打字、在标记边界打字、删除标记内容、全选删除、粘贴含换行文本、
  输入法组合输入中途打断——**都不产生错位、残留或正文缺字**；最坏结果是标记消失、文字保留。
- **光标与输入不回归**：连续快速打字不丢字、光标不跳；2000 字长块连续输入不卡顿。
- **容错**：正文含 `A = Aᵀ`、`[[1, 2], [2, 1]]`、`if (a == b)`、`{{1, 2}}`、`{{k:}}`（空内容）、`{{k:未闭合`
  时，只读态**逐字原样显示**，不吞字、不变形。
- **数据**：带标记文本保存 → 关闭 → 重开，标记与块级 `emphasis` 完整还原；
  导出 Markdown/HTML 无 `{{` 残留（代码块除外）；导出再导入后卡片色回到默认轮转（而非全灰）。
- **主题撞色检查**：把主题强调色依次设为 `赭土/苔绿/绛红/松石`，逐屏确认语义标记与焦点/控件不被读成同一件事。
- **回归**：`testDebugUnitTest` → `lintDebug` → `assembleDebug` 全绿；
  `MigrationTest.migrate5To6` 通过（需 `connectedDebugAndroidTest`）。
- **无障碍**：序号、标记角色需有 `contentDescription`；语义色不能是唯一信息载体（需同时有文字标签/粗体）；
  新动画在 `LocalReducedMotion = true` 时直接吸附不播放。
- **纯函数测试**：`InlineMarkupParserTest`（成对/未闭合/转义/空内容/跨行/嵌套/大小写/与 `**`、`` ` ``、`$` 的优先级）、
  `stripMarkup` 的一致性（渲染后再 `strip` 与直接 `strip` 结果相同）、
  `EmphasisTonesTest`（4 角色互异 + 映射到 `accentRoles`）、
  `CardAccentRotationTest`（前 5 项不同色族）、
  `notePreviewText` 剥离语法（扩展现有 `NotePreviewTextTest`）。
- **纯函数测试（v4 追加，编辑器改造的验收主体）**：
  `parse`/`materialize` 的**往返恒等**（对随机生成的合法文本做性质测试）、
  `adjustSpans` 的 8 条规则（含边界插入、零长 span、跨行断开）、
  `InlineMarkupNormalizer` 的 6 条规则 —— 其中必须有一条显式断言
  「**最坏结果只是标记消失，可见文字一字不少**」。

## 附二：本方案的决策清单（供评审打勾）

| # | 决策 | 结论 |
| --- | --- | --- |
| 1 | 内联语法载体 | `{{ }}`，**角色前缀必填**，无裸写、无"最近角色"状态 |
| 2 | 加粗 | 复用既有 `**粗体**`，不新增语法 |
| 3 | 三种笔触 | **进语法**，P2 同批交付（`-c` 纯变色 / `-u` 下划线，默认荧光笔） |
| 4 | 解析器归属 | 并入既有 `InlineLatex.kt` 词法器，固定优先级 代码 > 公式 > 加粗 > 语义色 |
| 5 | 语义色来源 | **派生自 `AccentPalette`**，不新写 hex、不新增 `darkEmphasisTone()` |
| 6 | 卡片身份色 | **保留**，显式推翻 _2026-09-30_ 第 87 行；色源取 `TagColors`（避开与 4 个语义角色逐值撞色）；改**显式轮转序** |
| 7 | `accent` 存储 | `INTEGER` 可空，存 `TagColors` 色值（同 `TagEntity.color`），`null` = 未设置（**不用 `0` 哨兵**） |
| 8 | `accent` 导出往返 | **接受丢失**（回落到轮转默认），不为此抬 `dtkVersion` |
| 9 | 迁移 | 一次 `Migration(5, 6)`，字段 `@ColumnInfo(defaultValue=…)` 与 DDL 对齐 |
| 10 | 卡片折叠 | 会话内状态；同时决定 `KnowledgeCard.isExpanded` 死字段的去留 |
| 11 | 卡内块 | **保持非 lazy**，sticky 只到卡片级；扁平化单独立项 |
| 12 | 三方色隔离 | 值隔离（身份色取 `TagColors`、语义色取 `AccentPalette.primary`）+ 位置隔离 + 四种主题色逐屏检查；退路是给语义色改用更深/更浅一档的自定义值 |
| 13 | 编辑态机制 | **标记不进编辑缓冲**（可见文本缓冲 + 会话内 span 表），**不用** `VisualTransformation` / 自定义 `OffsetMapping`；用户在任何状态都看不到标记 |
| 14 | 无选区点色块 | 进入「**标记中**」输入态：光标处放零长 span，随输入扩展；结束时若仍为零长则丢弃 |
